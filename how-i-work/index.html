How I work

An agent, here, means an AI tool given a task and allowed to act on its own for a while — reading files, writing code, making changes — rather than answering one question at a time. Anyone can get one to write code. The hard part is knowing when to believe the output. Trust comes from structure, not better prompting.

Contracts

An agent gets a written contract, with the autonomy boundary stated first

I run a personal knowledge base through an agent operating under a written contract. I produce thought; the agent owns structure. It files, links and propagates, and never asks me where something goes.

The contract fixes what would otherwise be re-litigated every run. Autonomy is stated up front as file freely, report after: placement is the agent's call, I veto afterwards. Ambiguous items stay queued rather than placed — an unfiled note is recoverable, a misfiled one vanishes — so the agent knows which way to err. Routing keys on what kind of fact something is, not its topic, which makes it decidable. Questions are batched and capped at five.

It also names its own anti-patterns. One tracking file is capped at five rows, because I once over-built a nineteen-item registry with rubrics and a dashboard and retired it; if it wants to grow, that is a signal to raise with me. The tag vocabulary is closed at five: one that grows without resistance stops separating anything. Blast radius is bounded too: two directories frozen, two files append-only, no git access.

Provenance

Every claim carries its source, and "not found" is a legal answer

Anything the agent writes is tagged with where it came from: a dated attribution, a git log, a file path. Unconfirmed claims are marked as such rather than smoothed over.

The rule doing the real work: never invent a fact, a number or a date, and NOT FOUND is a valid and preferred answer. Hallucination is not prompted against; it is designed out by making the absence of a fact expressible.

Guardrails

Enforce it in code, because a prompt is a hope

The clearest example is the market-data portal. Telling a model not to leak internal material is a hope; a build gate that fails the build when it happens is a guarantee. That gate exists because two real leaks got past an earlier exclusion operating at the rendering layer rather than the build layer.

Two more from the same build. Every factual claim on that site lives in a single data file, so claims are auditable in one place. And the sample-extraction tool raises on every unimplemented path, so it cannot emit a plausible-looking fabricated sample. Silence is the dangerous failure mode; the system fails loudly instead.

tools/check_no_leaks.mjs — the gate that fails the build

let leaks = 0;
for await (const file of walk(distDir)) {
  const text = await readFile(file, 'utf8');
  for (const { pattern, why } of FORBIDDEN) {
    const match = text.match(pattern);
    if (match) {
      console.error(`LEAK  ${relative('.', file)}\n      matched "${match[0]}" — ${why}`);
      leaks++;
    }
  }
}
if (leaks) {
  console.error(`\n${leaks} leak(s). Internal material must not ship. Fix before deploying.`);
  process.exit(1);
}

Acceptance criteria

Decide what counts as success before the run, not after

In the research work this is literal pre-registration: a written specification committed to version control, with a timestamp, before any result exists. It is what let me report that my own model failed its primary test, rather than re-cutting the metric until something passed.

The same device works on agent output: decide what done means after seeing the output and you will grade it on whatever it happened to do.

Fan-out and reconcile

Parallel agents produce contradictions; the value is in resolving them

I surveyed 53 project directories across parallel agents, each entry recording the surveying agent, a confidence rating, and a flag for credentials or personal data.

What mattered was the reconciliation afterwards: twelve ambiguities resolved by hand — which checkout was current, whether two repositories were one project, three similarly-named directories that proved unrelated. Fan-out is the cheap half; skipping reconciliation is how you get a confident, internally inconsistent answer.

Propagation

Filing is the easy half; the job is asking what a new fact contradicts

The agent's real task is checking new facts against what is recorded. Two catches, both against me.

Contradiction caught

A note about running an investment fund contradicted a career file that still listed starting one as a future goal. The goal was wrong; the fund already existed.

Overstatement caught, corrected downward

A build inventory claimed two founded ventures. Checking found that one was a five-person university course project and the other a solo side product with no revenue. Both CV bullets were rewritten downward, and both now read that way on this site.

Verification

Check what the agent says it did, including on this site

This site is the worked example. Contrast was checked programmatically across 30 colour pairs in both themes, not eyeballed. Overflow was measured at 390px and 1440px on every page — and the first harness produced a false positive, because headless Chrome clamps the window size and crops instead of reflowing. The bug was in the instrument, and surfaced only because the result was checked.

This is worth one sentence of context, because it is not obvious from outside: reporting a result that went against you is rare, and the reason is an incentive. When something comes out flat, the quiet option is to adjust the measurement and try again until it looks convincing, and nobody can tell afterwards. Fixing the target in advance is what removes that option, and it is why a null result I pre-registered is better evidence about me than a strong result I did not.

Lighthouse was not run, so no Lighthouse score is claimed anywhere on this site. Six figures the previous version advertised were found dead or revised against the current thesis draft, and are now listed in a committed rules file so they cannot creep back. That file is the build-gate principle again: write the constraint where it will be enforced, not where it will be remembered.
